Code Walkthrough — step1_ask_for_json.py

Demo script showing how to ask an LLM for JSON via HTTP, inspect the response step-by-step, and surface common failure modes when relying purely on natural-language instructions.

#!/usr/bin/env python3 # ============================================================================= # STEP 1 of 3 — ASKING FOR JSON IN THE PROMPT # ... Shebang for direct execution. Header comments frame this as Step 1: illustrating how to ask a model for structured JSON using only a prompt, and why that alone is fragile.
import json import requests PAUSE = True SERVER = "http://localhost:8080" Imports for JSON handling and HTTP calls. PAUSE controls interactive pauses; SERVER points to a local inference endpoint (e.g., llama.cpp/Open WebUI-style).
def pause(note): print() print(" " + "-" * 66) if PAUSE: input(" >>> " + note + " (press Enter to continue) ") else: print(" >>> " + note) print(" " + "-" * 66) print() Utility that segments output. When PAUSE is True, it blocks on Enter so learners can inspect prints/debugger state; otherwise just logs a separator.
# ============================================================================= # SECTION 1 — The raw material ticket_text = ( "Hi, this is Dervla Nolan from Aurora Freight. Our API integration " "started returning 502s at about 14:30 yesterday..." ) Simulated support ticket. Intentionally informal and noisy; used as the raw material to test how well a model can extract structured fields from messy human text.
print("THE TICKET AS THE CUSTOMER WROTE IT") print() print(ticket_text) pause("That is the input. It is just a string. Now we wrap instructions round it.") Echoes the raw ticket so learners confirm exactly what’s being fed in before adding instructions or prompts.
# ============================================================================= # SECTION 2 — Build the instruction instruction = ( "Extract the details from this support ticket.\n" "\n" "Return ONLY a JSON object with these three keys:\n" " customer_name - the person who wrote in\n" " company - the organisation they belong to\n" " severity - one of: low, medium, high, critical\n" "\n" "No explanation. No code fences. Just the JSON.\n" ) Defines explicit constraints: request exactly three fields as JSON and forbid extra prose or formatting. This is a common pattern to encourage machine-readable output.
prompt = instruction + "\nTicket:\n" + ticket_text print("THE FULL TEXT WE ARE ABOUT TO SEND TO THE MODEL") print() print(prompt) pause("This whole string is the input. The model sees nothing else.") Concatenates instructions with the raw ticket into a single message. Emphasizes that this complete block is all context the model receives.
# ============================================================================= # SECTION 3 — Build the request user_message = {} user_message["role"] = "user" user_message["content"] = prompt messages_list = [] messages_list.append(user_message) Builds a chat-style payload step-by-step for debugger visibility. Creates one “user” message containing the full prompt.
request_body = {} request_body["model"] = "local-model" # llama.cpp ignores this, but the API wants it request_body["messages"] = messages_list request_body["temperature"] = 0.0 # 0.0 = as predictable as possible request_body["max_tokens"] = 800 Assembles a standard OpenAI-compatible request body. temperature=0.0 reduces randomness; max_tokens caps response length to avoid runaway generation.
# --- turn the model's "thinking mode" off ----------------------------------- request_body["chat_template_kwargs"] = {"enable_thinking": False} request_body["reasoning_budget"] = 0 Explicitly disables extended internal reasoning/chain-of-thought in hybrid models, preventing verbose scratchpad text from consuming tokens or delaying the answer.
print("THE REQUEST BODY, AS JSON") print() print(json.dumps(request_body, indent=2)) pause("That dictionary is literally what travels over the network.") Prints the exact payload that will be POSTed so learners can inspect and validate it before making the actual request.
# ============================================================================= # SECTION 4 — Send it url = SERVER + "/v1/chat/completions" print("Sending to " + url + " ...") response = requests.post(url, json=request_body, timeout=120) Calls a standard chat completions endpoint with the JSON body and a long timeout (local inference can be slow). The HTTP response is stored in `response`.
print("HTTP status code:", response.status_code) # 200 means it worked pause("We have a response object. Now we dig the answer out of it.") Logs the HTTP status to confirm success before parsing; 200 indicates the server accepted and processed the request.
# ============================================================================= # SECTION 5 — Unpack the response, one layer at a time response_json = response.json() print("THE WHOLE REPLY") print() print(json.dumps(response_json, indent=2)) print() Deserializes and prints the full JSON reply so learners can see its nested structure before extracting pieces.
choices_list = response_json["choices"] # a list of possible answers first_choice = choices_list[0] # we only asked for one message_object = first_choice["message"] # the assistant's message reply_text = message_object["content"] # the actual words Navigates nested fields step-by-step to isolate the model’s primary response text, making it easier to trace in a debugger.
# Why the model stopped. "stop" vs "length". Always worth checking. finish_reason = first_choice.get("finish_reason") print("Why the model stopped :", finish_reason) print() Captures how generation ended: “stop” means normal completion; “length” means it hit max_tokens and may be truncated—critical for reliability.
# Some servers put internal monologue in its own field. thinking = message_object.get("reasoning_content") if thinking: print("The model also produced", len(thinking), "characters of private") print("thinking, in a separate 'reasoning_content' field...") ... Some endpoints expose a separate reasoning/scratchpad field. If non-empty here, the earlier disable flags didn’t take effect and tokens were spent on internal thought, not the answer.
print("JUST THE TEXT THE MODEL PRODUCED") print() print(repr(reply_text)) # repr() shows hidden characters pause("Look closely. Is that clean JSON, or is there something round it?") Uses `repr()` to reveal newlines, quotes, markdown fences, or extra prose that might look fine in a terminal but will break strict JSON parsing.
# ============================================================================= # SECTION 6 — Try to turn the text into data print("Attempting json.loads() ...") parsed = None try: parsed = json.loads(reply_text) except json.JSONDecodeError as error: print("FAILED - that string was not valid JSON.") ... Core validation step. `json.loads()` enforces real JSON; if it fails, the script branches into targeted diagnostics instead of silently proceeding with bad data.
if finish_reason == "length": print(" DIAGNOSIS: truncation.") ... If cut off by `max_tokens`, the JSON was never finished; suggests increasing token budget or ensuring reasoning mode is disabled so tokens go to actual output.
elif reply_text.strip() == "": print(" DIAGNOSIS: empty reply.") ... Empty content with a full thinking budget implies the model spent all its turns “thinking” and never wrote an answer, indicating flags in section 3 were ignored.
elif "{" in reply_text: print(" DIAGNOSIS: the JSON is in there, with something wrapped round it.") ... Model added conversational text or code fences around valid JSON, breaking strict parsing. Shows why “please return only JSON” is unreliable without a schema layer.
else: print(" DIAGNOSIS: no JSON at all. The model answered in prose...") Model ignored the instruction and answered in prose or refused, highlighting that natural-language prompts alone do not guarantee structure.
else: print("SUCCESS - we now have real data:") ... print(parsed["customer_name"], parsed["company"], parsed["severity"]) ... On success, prints extracted fields to confirm they match expectations—but then warns that this is compliance/probability, not a guarantee.
pause("Run this file four or five times. Do you get the same thing every time?") Encourages repeated runs to expose non-determinism and brittle reliance on model “cooperation,” motivating a stricter approach in step 2.
