Code Walkthrough — step1_by_hand.py

A single-turn, “by hand” walkthrough showing how an LLM agent uses tools via one API call.

Code Explanation
#!/usr/bin/env python3 # ============================================================================= # STEP 1 of 4 — ONE TURN, BY HAND # ============================================================================= ... # Run setup_sandbox.py first. # ============================================================================= Purpose and context.
  • This is Step 1 of a 4-part educational sequence showing how an LLM agent interacts with tools, one turn at a time.
  • The goal: demonstrate that what looks like “four human instructions” becomes fewer model actions via tool calls.
  • You are expected to step through this in a debugger (F6 = Step Over). The comments guide you not to dive into library internals.
import json import requests import pi_tools # our three tool functions. Read that file, then F6 past it. Imports.
  • json: serialize/deserialize JSON for API communication and parsing model arguments.
  • requests: HTTP client to call the LLM endpoint (OpenAI-compatible chat completions style).
  • pi_tools: local module that defines:
    • The tool schemas sent in the request.
    • A dispatch map from function names → real Python functions actually running on “the Pi.”
# --- scaffolding, not part of the lesson ---- PAUSE = True SERVER = "http://localhost:8080" def pause(note): print() print(" " + "-" * 66) if PAUSE: input(" >>> " + note + " (press Enter to continue) ") else: print(" >>> " + note) print(" " + "-" * 66) print() Interactive scaffolding.
  • PAUSE = True: when enabled, each section waits for you to press Enter—so you can inspect output before moving on.
  • SERVER: base URL of a local LLM gateway (likely something like llama-cpp or similar) exposing an OpenAI-style /v1/chat/completions endpoint.
  • pause(note): helper that prints a visual separator and prompts you; used to chunk the “lesson” into readable beats.
# ============================================================================= # SECTION 1 — What the user asked for # ============================================================================= task = ("Log on to the Pi, go to my home directory, find all the .tmp files " "and delete the largest one if there is one.") print("THE TASK") print() print(" " + task) pause("Four instructions, the way a person would say them. Hold that thought.") Define the user’s request in natural language.
  • This is intentionally human-like and slightly ambiguous—exactly how users talk to agents.
  • The print + pause highlights: “This is what a person would say.” You’ll later see why only parts of this are meaningful as tool actions.
# ============================================================================= # SECTION 2 — Two things the model will never do # ============================================================================= print("WHAT THE MODEL CAN ACTUALLY DO") ... print(" list_files(directory, pattern) -> names and sizes") print(" delete_file(path) -> deletes ONE file") ... pause("Open pi_tools.py and look at the two schemas near the bottom.") Clarify what “logging in” and “cd ~” mean for an agent.
  • The user prompt says “Log on to the Pi” and “go to my home directory,” but:
  • These are not model actions—the connection, auth, and base path are handled by our code (via environment or config in pi_tools.py).
  • The model only sees two abstract tools:
    • list_files(directory, pattern)
    • delete_file(path)
  • This illustrates a key point: agent prompts often include “flavor” instructions that map to environment setup, not model behavior.
# ============================================================================= # SECTION 3 — Build the message list # ============================================================================= system_prompt = ("You are a careful assistant with access to a Raspberry Pi. " "Use the tools rather than guessing. When the task is done, " "say so in one sentence and stop calling tools.") system_message = {} system_message["role"] = "system" system_message["content"] = system_prompt user_message = {} user_message["role"] = "user" user_message["content"] = task messages = [] messages.append(system_message) messages.append(user_message) print("THE MESSAGE LIST (" + str(len(messages)) + " items)") ... pause("Two items. Remember that number.") Initialize the conversation history.
  • system_prompt: sets behavior: use tools, avoid guessing, announce completion once done and stop.
  • We build two messages:
    • {"role": "system", ...}
    • {"role": "user", "content": task}
  • This matches the standard OpenAI-style chat format.
  • The pause reminds you: right now, history = exactly two messages. In a full agent loop this list grows with each turn.
# ============================================================================= # SECTION 4 — Build the request # ============================================================================= tools = [] tools.append(pi_tools.LIST_FILES_SCHEMA) tools.append(pi_tools.DELETE_FILE_SCHEMA) request_body = {} request_body["model"] = "local-model" request_body["messages"] = messages request_body["tools"] = tools request_body["temperature"] = 0.0 request_body["max_tokens"] = 800 # Thinking mode off - see lab 2's walkthrough for why this matters. request_body["chat_template_kwargs"] = {"enable_thinking": False} request_body["reasoning_budget"] = 0 Assemble the API payload.
  • tools: list of tool schemas (JSON Schema-like descriptions) telling the model:
    • What tools exist.
    • What arguments each expects.
  • "model": "local-model": identifier used by your local server (often ignored but required).
  • temperature = 0.0: deterministic behavior—important when testing tool calling; we want predictable choices.
  • The “thinking” flags disable internal chain-of-thought style reasoning to keep output clean and focused on tool calls.
print("WHAT WE ARE SENDING") ... print(" The tool schemas are", len(json.dumps(tools)), "characters.") print(" They go over the wire on EVERY call. Remember that too.") pause("Now send it. F6, not F5.") Emphasize cost and overhead.
  • This reminds you:
    • We are shipping the full tool schemas on every single request (latency + token cost).
    • In real agent systems, that’s a non-trivial consideration for many tools or frequent calls.
  • The “F6, not F5” note is debugger-specific: Step Over the HTTP call so you don’t fall into library internals.
# ============================================================================= # SECTION 5 — Send it # ============================================================================= url = SERVER + "/v1/chat/completions" print("Sending to " + url + " ...") response = requests.post(url, json=request_body, timeout=180) print("HTTP status:", response.status_code) if response.status_code == 400: print() print("A 400 here almost always means llama-server was started without") print("--jinja, so it has no tool-calling template. Add it and restart.") raise SystemExit(1) Make the first (and only) API call in this file.
  • Sends JSON payload to a local OpenAI-style completions endpoint.
  • timeout=180: up to 3 minutes allowed; LLM inference can be slow, especially locally.
  • The 400 guard is practical: if the server was launched without proper templating (--jinja) it won’t support tool-calling prompts and returns a 400. The script fails fast with guidance instead of confusing output.
# ============================================================================= # SECTION 6 — What came back # ============================================================================= response_json = response.json() choices_list = response_json["choices"] first_choice = choices_list[0] message_object = first_choice["message"] finish_reason = first_choice["finish_reason"] print("finish_reason :", repr(finish_reason)) ... if finish_reason == "tool_calls": print(" -> the model wants a tool run. The conversation is NOT over.") else: print(" -> the model thinks it is done. (Unexpected this early.)") Interpret what the model decided to do.
  • We unpack response.json()["choices"][0], focusing on:
  • finish_reason:
    • "tool_calls": model believes a tool should run → conversation continues.
    • "stop": model thinks it’s done; in this script that would be unexpected on turn one.
  • This is exactly the branching logic an agent loop would use: “tool_calls” means keep going; “stop” means end conversation.
print() print("Anything in 'content'?", repr(message_object.get("content"))) print() print("THE TOOL CALL") ... print(json.dumps(message_object["tool_calls"], indent=2)) pause("It asked for list_files. Look at the pattern it chose.") Show the model’s tool call.
  • content: often empty when the model only emits a tool call (no chatty explanation).
  • We print tool_calls, which includes:
    • Which tool to use.
    • The arguments it wants to pass (as JSON string).
  • In this case, the model calls list_files with a pattern like “*.tmp” in the home directory—exactly what we’d expect.
# ============================================================================= # SECTION 7 — Run the tool *** our decision, not the model's *** # ============================================================================= tool_calls = message_object["tool_calls"] first_call = tool_calls[0] call_id = first_call["id"] # we must quote this back called_function = first_call["function"] function_name = called_function["name"] arguments_text = called_function["arguments"] # a STRING, not a dict arguments = json.loads(arguments_text) print(" name :", function_name) print(" arguments :", arguments) ... tool_function = pi_tools.DISPATCH.get(function_name) Extract and validate the requested tool call.
  • We read:
    • call_id: needed to correlate results back in a real loop (not used here yet).
    • function_name and JSON-decoded arguments.
  • The DISPATCH dict in pi_tools maps allowed names (e.g., "list_files") → real Python callables. This is a safety boundary: the model cannot invent new tools.
if tool_function is None: tool_output = "ERROR: no such tool: " + function_name else: tool_output = tool_function(**arguments) print("WHAT THE TOOL RETURNED") ... for line in tool_output.splitlines(): print(" " + line) pause("The model has not seen any of that yet. It is just sitting in a variable.") Run the real operation.
  • If unknown: return an error string instead of crashing—this would be fed back into the LLM as “tool output” in a full loop.
  • Otherwise, call tool_function(**arguments): e.g., it lists files matching *.tmp with sizes.
  • Critical point (highlighted by pause): this result currently lives only in our code; the model does not know what we found until we send another request that includes it. That’s why a second file (step2) is needed to continue.
# ============================================================================= # WHAT TO TAKE AWAY # ============================================================================= ... print() print("Finished one turn. We now hold a result the model has never seen.") print() print("Next: python step2_by_hand.py") Core lesson.
  • This script proves three ideas by hand, in one clean pass:
  • 1) The natural-language prompt is decomposed into tool calls (not literal shell steps).
  • 2) Tool calling is asynchronous and stateless: model outputs a call → we run it → result must be fed back.
  • 3) A real agent loop is just repeated versions of this: append results to messages, call again, until finish_reason == "stop".
  • The final print nudges you toward Step 2 where the conversation continues with the new information.
